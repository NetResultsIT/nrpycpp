# nrPyCpp workspace rules

nrPyCpp is a Qt 6 C++17 library that embeds CPython 3.13 so that C++ code can call Python functions
(`PyRunnerQt`). It is built with qmake (`lib/nrPyCpp.pro`) for macOS, Linux and Windows, and it is public on
GitHub. VDK links it. Changes go to `master` of the public repository through pull requests; the repository also
has the branches `release`, `release-1.x` and `v1.x` (their purpose is not verified).

## 1. Other people and agents work here too
- Do not run git commands that move a checkout someone else uses (checkout, reset, clean, stash) and do not
  overwrite its build output (`lib/last_build`, `build-tests`, `build/`) or its python runtime (the folder
  `NRPYCPP_PYTHON_ROOT` points to, `lib/depspath.pri`). Work in a separate git worktree unless told to use the
  current one.
- Keep each file's line endings. Every tracked source, script and doc checked is LF; new files use LF.
- Delete only what your own session created, by explicit path, never with a wildcard and never outside the project
  folder; ask before deleting anything else (branches, worktrees, build folders, dependency folders).
- Commit or push only when asked.
- This repository is public: no internal host names, URLs, credential file names or personal paths in any file you
  write, and no secrets.

## 2. Stop and ask first
You need the user's explicit consent before:
1. changing the public API: the headers packaged for users (`DIST_INCS` of `lib/nrPyCpp.pro`: `PyCall.h`,
   `PyCallBackIface.h`, `nrPyCppConfig.h` and the generated `PyRunnerQt.h`), the `NRPYQT_LIB_API` classes, the
   methods between the `START_WRAPPER_METHODS` markers of `lib/pyrunner.h` with `lib/nrpycpp_wrapper_conf.json`,
   the `NRPYCPP_PYTHON.json` package description. A change or removal breaks compatibility and needs a new major
   version: propose the compatible way first (new API, the old one deprecated and forwarding to it), and make the
   breaking change only when the user explicitly acknowledges the new major (skill `semver-abi`);
2. changing threading: new threads, mutexes, lock order, the one thread per runner and the single shared
   interpreter and GIL (`docs/USAGE.md` section 6; `PyEnvironment` starts and stops it);
3. changing contracts: the Python to C++ type conversions (`docs/USAGE.md` section 3), the error reporting through
   `PyFunctionCallResult`, the `nrpycpp` module that scripts import, the python home search order of
   `nrPyCppConfig.h`;
4. adding or removing files in the build files (`lib/nrPyCpp.pro`, `tests/nrPyCppTests.pro`,
   `tester/nrPyCppTester.pro`), or changing the python runtime version or the package layout;
5. publishing or deleting anything outside the repository: python packages, library packages, tags, CI settings;
6. adding a third-party component or changing one's license, or changing the license of this library (MIT, file
   `LICENSE`); the user confirms that a component's license fits the company policy ("it is the same license as X"
   is a suggestion, not the confirmation).
State what you want to change and why, and wait.

## 3. Lead and worker
Non trivial changes (a feature, a bug fix, a refactoring) follow skill `nrpycpp-dev-workflow`:
1. the lead model reads the code, designs the tests first, and writes the plan;
2. the lead stops at the gate of section 2 when the plan touches it;
3. a worker on a lighter model implements the plan and runs the tests;
4. the lead reviews the diff and the test output, and reports.

| Tool | Lead | Worker |
|---|---|---|
| Claude Code | the session model | `Agent` tool with a lighter model (`sonnet`, `haiku`) |
| Gemini CLI / Antigravity | the session model (Pro) | `invoke_subagent` with `Model: "flash"` |
| Codex and others | the session model | the tool's subagent or a second session on a smaller model |

A change of a few lines that the lead can verify alone does not need a worker.

## 4. Conventions
- Versioning (skill `semver-abi`): the ABI is kept within a major; a bug fix is a patch, a new feature or anything
  new a user can call is a minor, a changed or removed public API is a major. The version is `NRPYCPP_VERSION` in
  `lib/nrPyCpp.pro` (2.0.1; the tag `v2.0.0` exists): version 2 is released, so the rule applies to every change.
- Errors: a call returns a `PyFunctionCallResult` with `error` and `errorMessage` (with the Python traceback); the
  public API does not throw. Details: `docs/USAGE.md` section 4.
- `lib/PyRunnerQt.h` and `lib/PyRunnerQt.cpp` are generated by wrappergen from `lib/pyrunner.h`; they are not in
  the repository tree and are never edited by hand. Regenerate and check: `docs/BUILDING.md` section 5.
- `depspath.pri`, `config.pri` and `qac.version` are local and git-ignored (`.gitignore`): do not commit them.
- Keep `docs/USAGE.md` and `docs/BUILDING.md` in step with the code; the python package layout is in
  `docs/BUILDING.md` section 2 and is produced by `tools/prepare_python_runtime.py`.

## 5. Skills
| Skill | Use it when |
|---|---|
| `nrpycpp-dev-workflow` | planning, implementing or reviewing any change; building and testing the library |
| `nrpycpp-python-deps` | preparing, testing or publishing the python runtime package; python home and debug build issues |
| `qt-cpp` | writing or reviewing Qt C++: objects and threads, connections, timers, Qt Test, Qt 6.8 traps |
| `semver-abi` | a change touches public API, an enum, a JSON format or an error code; adding a feature; a release |

The skills are edited in `.agents/skills`; `.claude/skills` is a copy made by `tools/sync_skills.py`; the
pre-commit hook runs its `--check` (enable it once per clone: `git config core.hooksPath .githooks`). The shared
skills (`qt-cpp`, `semver-abi`) are copies from the `agent-skills` repository, pinned in `.agents/shared-skills.lock`:
they are not edited here.

## 6. Where new knowledge goes
What you learn while working (a missing build step, a trap, a wrong statement in these files) is written down in the
same change, in one place: the table is in skill `nrpycpp-dev-workflow`, "Where new knowledge goes". Correct a wrong
statement where it stands instead of adding a note. A worker reports what it learned; the lead decides where it
goes and reviews the edit like code.
